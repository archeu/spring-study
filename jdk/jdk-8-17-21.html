JDK 8 · 17 · 21 · LTS · JEP · AMBER · LOOM · G1 / ZGC · 模块与强封装

从 8 到 21，Java 改了什么、为什么改

8、17、21 不是三个孤立的版本，而是一条线上的三个长期支持（LTS）站点：17 包含了 9 到 16 的全部改动，21 又包含了 18 到 20。这些改动可以归成四条主线：写代码更省事（record、模式匹配）、并发更便宜（虚拟线程）、GC 停顿更短（G1、ZGC）、平台更好维护（模块和强封装，删掉旧东西）。前三条是升级的好处，第四条是升级时踩坑的来源。

①为什么学→ ②老办法→ ③选谁→ ④原理→ ⑤跑起来→ ⑥细节→ ↺回到⑤

假设场景团队的老服务还跑在 JDK 8 + Spring Boot 2 上，新项目要上 Spring Boot 3，它最低要 JDK 17；新同事写的代码里出现了 record、var、switch 里的 ->；面试也常问“8 到 17 有什么变化”。本页按你的要求没有在本机运行任何代码，版本和行为都按 JEP、OpenJDK 源码和发行商文档核对，代码示例标了“未在本机运行”。

①为什么学：三个版本，隔着十年

8 是 2014 年的，21 是 2023 年的。中间 Java 换了发布节奏，每半年出一个版本，每两三年挑一个做长期支持。

工作要用

Spring Boot 3 和 4 最低都要 JDK 17（Boot 4.1.2 的 class 文件版本是 61，即 17）。不升级 JDK，框架就升不上去。

看得懂新代码

record、sealed、switch 模式匹配、文本块、var、虚拟线程，在 8 上全都不存在。

升级不出事故

升级时 JVM 起不来、反射报错、类找不到，大多来自“平台治理”这条线。知道它为什么改，就知道去哪改。

②老办法：留在 JDK 8，靠第三方库补

很多团队就是这么过来的：语言缺什么，就引一个库补上。能做，但有几样补不上。

疼在哪

库能补的是 API 和语法糖；补不上的是要改编译器、JVM、类库内部的东西：编译器检查、线程实现、GC、字符串的内存布局。还有一样最实际：框架生态已经往前走了。

所以升级的精华：拿到只有平台自己能做的改进，同时还清“平台治理”这条线欠下的账。

典型误用以为升级就是换个 JDK 安装包、改一下 JAVA_HOME。8 到 17 中间有一整段“删旧东西、关后门”的改动（模块强封装、删 Java EE 模块、删 CMS 和老 GC 参数），不知道它们为什么删，就只能见一个错改一个（⑥ 第一圈）。

③选谁：长期支持版怎么挑

生产只用长期支持版（LTS），中间版本只有半年的更新。LTS 不是语言规范里的概念，是各家发行商（Oracle、Eclipse Temurin、Amazon Corretto、阿里 Dragonwell 等）承诺给这个版本出几年补丁。

选择规则：新项目直接 21（依赖都支持的话可以考虑 25）；要用 Spring Boot 3 / 4 的至少 17；老项目卡在 8 的，跳过 11 直接规划到 17 或 21，因为 9 到 17 的坑反正都要过一遍。本页学 8 → 17 → 21 这一段改了什么、为什么。

④原理：一种发布方式，四条主线

先看 Java 现在怎么出版本（这决定了 8、17、21 的关系），再看 8 到 21 的改动分成哪四条线、每样新东西是为了解决什么问题，最后看几处“为什么非这样设计不可”。

先知道这些

JDK、JRE、JVM

JVM 执行字节码；JRE = JVM + 类库；JDK = JRE + javac 等工具。9 起官方不再单独发 JRE，用 jlink 按需裁一个运行时。

JEP

JDK Enhancement Proposal，每个新特性的提案和编号，比如 JEP 444 是虚拟线程。本页的“哪个版本”都按 JEP 写的目标版本。

预览特性

先放进版本里让大家试，编译和运行都要加 --enable-preview，下个版本可能改、也可能删。转正之后才算数。

LTS

发行商对某个版本的长期补丁承诺，不是语言特性。11、17、21 和 8 在语言上没有“特殊”，只是补丁出得久。

机制 1发布方式：从“等大特性”到“半年一班车”8、17、21 的关系由它决定

以前：版本等最大的那个特性到 JDK 9 为止

现在：每半年发一班车从 JDK 10 起

决定这个设计的约束：大特性的完成时间没法预测。绑在一起发，小改进跟着等；拆成定期发车，每个特性单独上车，语言新语法还能先以“预览”身份收反馈。后果有两个：一是 17 和 21 只是其中两班车，17 = 8 + 9～16 所有班车的内容；二是不少特性在中间版本里已经出现过预览，到 LTS 才转正（record 14、15 预览，16 转正）。

机制 28 到 21 的四条主线点在哪一列，就是在哪个版本转正

机制 3为什么是 record + sealed + 模式匹配，而不是 Lombok设计对比

  • Lombok 的 @Data 是在编译时改语法树，生成的是普通类：编译器不知道它“只是数据”，没法拿它做解构，更没法做穷尽检查。它还要用 javac 的内部 API，所以每次升级 JDK 都要跟着升 Lombok（⑥ 第三圈）。
  • Visitor 模式也能保证“每种都处理到”，但要给每个类型加 accept 方法，新增一种操作要改所有类。
  • record 是语言层面的声明：字段就是全部状态、不可变，所以模式匹配能安全地把它拆开（case Paid(var id, var cents)）。
  • sealed 告诉编译器“就这几种”，switch 模式负责按类型分支。三样拼在一起，就是函数式语言里的代数数据类型：新增一种情况时，编译器把所有该改的地方列出来。

机制 4为什么要强封装：让 JDK 能改自己的内部设计对比

JDK 8：类路径上一切可见

JDK 17：只导出公开的包

决定这个设计的约束：JDK 要持续重构内部（压缩字符串、虚拟线程都改了 String、Thread 的内部），而一大批库依赖着这些内部。不封起来，每次重构都会打坏别人，JDK 就只能停在原地。9 先给警告，16 默认拒绝，17 去掉一键放开的开关，前后给了生态四年多时间迁移。坏掉的老库，修法是升级库本身，--add-opens 只是过渡。

语法21 的写法，最少要认得这些每行注明是哪个版本来的

PayResults.java未在本机运行；按 JEP 395 / 409 / 440 / 441 / 444 的写法核对
sealed interface PayResult permits Paid, Failed, Pending {}            // 17 sealed
record Paid(String orderId, long cents) implements PayResult {}         // 16 record
record Failed(String orderId, String reason) implements PayResult {}
record Pending(String orderId) implements PayResult {}

static String describe(PayResult r) {
    return switch (r) {                                                   // 14 switch 表达式
        case Paid(var id, var cents) -> id + " 已付 " + cents / 100.0;    // 21 record 模式
        case Failed f when f.reason().isBlank() -> f.orderId() + " 失败";  // 21 带条件的 case
        case Failed f -> f.orderId() + " 失败：" + f.reason();
        case Pending p -> p.orderId() + " 处理中";
    };                                                                    // 没有 default：漏一种就编译不过
}

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {          // 21 虚拟线程，10 var
    exec.submit(() -> query(orderId));
}

参数、GC 选择、各个特性的边角规则放到第⑥步。注意带 when 的 case 要写在同类型的普通 case 前面，否则会被它“盖住”而编译报错。

⑤跑起来：同一段代码，8 和 21 各写一遍，再升一次级

一个小场景：拿到一批支付结果，按类型生成描述，再并发查 1000 个订单。左边是 JDK 8 的写法，右边是 21 的写法。代码未在本机运行，写法按 JEP 和 JLS 核对。

JDK 8Lombok + instanceof + 固定线程池
interface PayResult {}
@Value class Paid implements PayResult {      // Lombok 生成
    String orderId; long cents; }
@Value class Failed implements PayResult {
    String orderId; String reason; }
@Value class Pending implements PayResult {
    String orderId; }

static String describe(PayResult r) {
    if (r instanceof Paid) {
        Paid p = (Paid) r;                      // 判断完还要强转
        return p.getOrderId() + " 已付 " + p.getCents() / 100.0;
    } else if (r instanceof Failed) {
        Failed f = (Failed) r;
        return f.getOrderId() + " 失败：" + f.getReason();
    } else if (r instanceof Pending) {
        return ((Pending) r).getOrderId() + " 处理中";
    }
    throw new IllegalStateException();          // 漏了一种，运行时才知道
}

// 1000 个阻塞查询：池子 200，其余排队
ExecutorService pool = Executors.newFixedThreadPool(200);
List<Future<Order>> fs = new ArrayList<>();
for (String id : ids) fs.add(pool.submit(() -> query(id)));
for (Future<Order> f : fs) f.get();
pool.shutdown();

sealed interface PayResult permits Paid, Failed, Pending {}
record Paid(String orderId, long cents) implements PayResult {}
record Failed(String orderId, String reason) implements PayResult {}
record Pending(String orderId) implements PayResult {}

static String describe(PayResult r) {
    return switch (r) {
        case Paid(var id, var cents) -> id + " 已付 " + cents / 100.0;
        case Failed(var id, var reason) -> id + " 失败：" + reason;
        case Pending(var id) -> id + " 处理中";
    };                                // 漏了一种：编译不过
}





// 1000 个阻塞查询：每个一个虚拟线程，同时进行
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    var fs = ids.stream()
                .map(id -> exec.submit(() -> query(id)))
                .toList();            // 16 Stream.toList
    for (var f : fs) f.get();
}                                     // 19 起 ExecutorService 能用 try-with-resources，退出时等任务做完
pom.xml用 release，而不是 source / target
<properties>
    <maven.compiler.release>21</maven.compiler.release>   <!-- 用了 Spring Boot 父 POM 时写 <java.version>21</java.version> -->

release（9 起）同时限定语法和可用的 JDK API；只写 source/target 时，高版本 javac 会放过只有新 JDK 才有的方法，程序拿到老 JDK 上才报 NoSuchMethodError。ExecutorService 实现 AutoCloseable 是 JDK 19 加的，21 里能直接用。

老项目从 8 升到 17 / 21：五步

  1. 1先扫一遍。jdeps --jdk-internals app.jar 列出用到的 JDK 内部 API；jdeprscan --release 17 app.jar 列出用到的已弃用、已删除 API。两个工具 JDK 9 起自带。
  2. 2先升依赖，再换 JDK。Lombok、Spring、ASM / cglib、Mockito、字节码类 APM、Maven 编译插件都要升到支持目标 JDK 的版本，这一步解决大部分强封装问题。
  3. 3换 JDK 编译。改成 release；补上被移出 JDK 的依赖（JAXB 等）；内部类换成公开 API。
  4. 4改启动参数。删掉 CMS、PrintGCDateStamps、PermSize 等老参数；GC 日志改成 -Xlog:gc*:file=gc.log:time,uptime；容器里用 -XX:MaxRAMPercentage 代替写死的 -Xmx。
  5. 5测、压、灰度。跑全量测试，压测对比 GC 停顿和 RT（默认 GC 从 Parallel 变成了 G1），再灰度上线。

⑥细节：升级时会在哪出事

第一圈是升级时最常见的坑，按“起不来 → 编译不过 → 运行报错 → 悄悄变了”排，每条标了根源在 ④ 的哪一条；第二圈是团队规范；第三圈是几处更深的原因，最后是升级检查器。

第一圈

注意事项

坑 1换上新 JDK，JVM 直接起不来← ④ 机制 2 GC 线
现象
Unrecognized VM option 'PrintGCDateStamps'，接着 Error: Could not create the Java Virtual Machine.
根源
9 起 GC 日志统一成 -Xlog，PrintGCDateStamps 这类老参数被删；UseCGroupMemoryLimitForHeap 在 11 里已不认识；CMS 在 14 被删时只是警告并忽略，15 起 -XX:+UseConcMarkSweepGC 也成了不认识的参数（按 jdk11u、14u、15u 的 arguments.cpp 核对）。而 MaxPermSize 只打警告，不影响启动。
做法
升级前先把启动脚本里的 GC 参数清一遍：日志改 -Xlog:gc*:file=gc.log:time,uptime，CMS 删掉用默认 G1，容器用 MaxRAMPercentage。
坑 2编译通过，一跑就报 InaccessibleObjectException← ④ 机制 4 强封装
现象
Unable to make field private final byte[] java.lang.String.value accessible: module java.base does not "opens java.lang" to unnamed module
根源
老版本的 Lombok、cglib、Mockito、序列化库或自己的代码，用反射改 JDK 内部字段。9～15 只打警告，16 默认拒绝，17 删掉了 --illegal-access 总开关。
做法
升级这些库到支持目标 JDK 的版本；实在等不及，按包加 --add-opens java.base/java.lang=ALL-UNNAMED，并记一笔技术债。
坑 3ClassNotFoundException: javax.xml.bind.JAXBContext← ④ 机制 2 治理线
现象
在 8 上好好的，换 11 以上编译不过，或者运行时找不到 JAXB、JAX-WS、javax.annotation 的类。
根源
JEP 320 在 11 把 Java EE 和 CORBA 模块移出了 JDK，它们本来就属于 Java EE。
做法
加对应的 Maven 依赖（如 jakarta.xml.bind-api 加一个实现）。要上 Spring Boot 3 的，直接用 jakarta 版本。
坑 4升 Spring Boot 3，一大片 import 报红历史原因：Java EE 改名
现象
javax.servlet、javax.persistence、javax.validation 全都找不到。
根源
这不是 JDK 的改动：Java EE 移交 Eclipse 基金会后改名 Jakarta EE，从 Jakarta EE 9 起包名从 javax.* 改成 jakarta.*。Spring Boot 3 基于 Jakarta EE 9+，又要求 JDK 17，两件事常被混成一件。
做法
先升到 Boot 2.7 最新版、清掉弃用警告，再按官方迁移指南批量改包名（IDE 和 OpenRewrite 都有现成的迁移规则）。
坑 5没报错，但中文乱码、日期格式变了← ④ 机制 2 治理线
现象
升到 21 后，中文 Windows 上读出来的文件乱码；或者升到 9 以上，某些语言的日期、数字格式化结果和以前不一样。
根源
18 起（JEP 400）不写编码时默认用 UTF-8，不再跟操作系统走，以前按 GBK 读写的代码行为就变了。9 起（JEP 252）默认的本地化数据换成了 CLDR。
做法
读写文件、转字节一律显式写 StandardCharsets.UTF_8；格式化写死 pattern 和 Locale。过渡期可用 -Dfile.encoding=COMPAT、-Djava.locale.providers=COMPAT,CLDR（后者在 21 里已标记要删）。
坑 6用了预览特性，下个版本代码就废了← ④ 机制 1 预览
现象
21 上用 STR."…" 字符串模板写的代码，升到 23 编译不过。
根源
预览特性可以改、也可以删。字符串模板（JEP 430）在 21、22 是预览，23 里被整个撤掉。另外预览特性编出来的 class 只能在同一个 JDK 版本上跑。
做法
生产代码不用 --enable-preview。21 里的结构化并发、ScopedValue、未命名变量都是预览，等转正再用。
坑 721 上 Arthas 一 attach 就打警告← ④ 机制 2 治理线
现象
日志里出现 “A Java agent has been loaded dynamically … dynamic loading of agents will be disallowed by default in a future release”。
根源
JEP 451：运行中动态注入的 agent 能改任何代码，JDK 要逐步收紧，21 先打警告。
做法
APM 改成启动参数 -javaagent；需要临时 attach 排查的服务，启动时加 -XX:+EnableDynamicAgentLoading。
坑 8开了虚拟线程，压力一大全卡住← ④ 机制 2 并发线
现象
21 上打开 spring.threads.virtual.enabled，平时正常，高峰时请求全部不动。
根源
21 里虚拟线程在 synchronized 块里阻塞会钉住载体线程，载体线程默认和 CPU 核数一样多；24（JEP 491）才解决。下游连接池也会变成新瓶颈。
做法
用 JFR 事件 jdk.VirtualThreadPinned 找钉住点，换 ReentrantLock；对下游加并发上限。详见 网络 IO 模型 · 坑 7。

使用规范

第三圈

更深一层

为什么每升一次 JDK，Lombok 都要跟着升

Lombok 不是普通的注解处理器：标准注解处理器只能生成新文件，不能改已有的类；Lombok 要在你的类里加 getter，只能拿到 javac 内部的语法树直接改。javac 的内部 API 不保证兼容，加上 16、17 的强封装，每个新 JDK 都可能让旧 Lombok 失效。record 是语言自己提供的，不存在这个问题。

默认 GC 换了，升级后要看什么

  • 8 默认 Parallel（吞吐优先），9 起默认 G1（停顿优先）。同样的堆，升级后吞吐可能略降、停顿明显变短，压测要两样都看。
  • 21 的 ZGC 要分代的话，得加 -XX:+UseZGC -XX:+ZGenerational；23 起分代成了默认，24 删了不分代的模式。
  • 容器里 JVM 只拿到 1 个 CPU、内存小于约 1792 MB 时，会自动选 Serial GC。规格太小的 Pod 要显式指定 GC。

为什么 17 和 21 都要“删东西”

每一样留在 JDK 里的东西都有维护成本：CMS 拖累 GC 代码重构，SecurityManager 让每个敏感操作都要多一层权限检查，Nashorn 要追 JS 标准。Java 的承诺是“公开 API 尽量兼容”，所以删之前都会先弃用、打警告，给几个版本的缓冲。升级时看一眼 jdeprscan 的输出，就能提前知道下一次会坏什么。

17 到 21 其实改得不多，为什么值得升

语言上主要是模式匹配补齐了（record 模式、switch 模式），API 上是 SequencedCollection；真正的分量在运行时：虚拟线程和分代 ZGC。如果服务是“大量阻塞 IO + 线程池不够用”，或者大堆、对停顿敏感，21 的收益最直接；如果都不是，17 → 21 的升级风险也很小（主要是坑 5、7、8，外加用了 SecurityManager 的会在 18 起报错）。

练习 1 · 加一种状态

给 21 版加 record Refunded(String orderId, long cents)，并加进 permits，不改 describe，编译。

做对了会看到：编译失败，提示 switch 没有覆盖所有可能的输入。8 版加一个 Refunded 类则能编译通过，运行到它时才抛 IllegalStateException。

用到：④ 机制 3、第二圈“不写 default”

练习 2 · 扫自己的项目

在公司项目上跑 jdeps --jdk-internals 和 jdeprscan --release 21，再把启动脚本里的 -XX 参数逐个对照坑 1。

做对了会看到：一份“内部 API → 建议替代”的清单；常见的是 sun.misc.Unsafe（多半来自依赖）和 sun.misc.BASE64Encoder（换 java.util.Base64）。

用到：⑤ 五步、坑 1、坑 2

练习 3 · 先猜，再看线程数

把 8 版的 1000 个查询（每个阻塞 1 秒）分别用固定 200 线程池和 21 的虚拟线程跑，先猜两者大约各要几秒。

做对了会看到：线程池约 5 秒（1000 ÷ 200 批，每批 1 秒）；虚拟线程约 1 秒，前提是 query 背后的连接池也撑得住 1000 个并发，否则瓶颈挪到连接池。

用到：坑 8、三高 · Little 定律

1. 用一句话说出 8、17、21 的关系和升级的精华。

它们是半年一班车里的三个长期支持站点，17 包含 9～16、21 包含 18～20 的全部改动；升级拿到的是只有平台能做的改进（编译器检查、虚拟线程、GC、字符串布局），要还的是“平台治理”那条线的账（强封装、删模块、删旧参数）。

← 开头 + ②

2. 留在 JDK 8 靠第三方库补，痛在哪？

库只能补 API 和语法糖，补不了要改编译器、JVM、类库内部的东西（穷尽检查、虚拟线程、新 GC、压缩字符串）；而且 Spring Boot 3 / 4 最低要 17，框架生态已经往前走了。

← ②

3. “编译通过、一跑就报 InaccessibleObjectException”，根源是 ④ 的哪一条？

机制 4 强封装：为了让 JDK 能改自己的内部，9 起用模块划清公开和内部，16 默认拒绝反射访问内部，17 去掉了总开关。老库用反射改 JDK 私有字段，就撞上了。

← ④ 机制 4 + 坑 2

4. 预测：JDK 8 的服务，启动脚本里有 -XX:+UseConcMarkSweepGC -XX:MaxPermSize=256m，直接换 JDK 14 和 JDK 17 各会怎样？

14：两个参数都只打“Ignoring option …”警告，JVM 照常启动，GC 悄悄变成默认的 G1。17：CMS 参数在 15 起已经不认识，JVM 报 Unrecognized VM option 起不来；MaxPermSize 仍只是警告。

← 坑 1（按 HotSpot 源码里的过期表推出）

5. 预测：sealed interface Shape permits Circle, Square，某处 switch 写了 default -> 0。后来加了 Triangle，这个 switch 会怎样？

照样编译通过，Triangle 走进 default 返回 0，悄悄算错。写了 default，编译器就认为你已经处理了“其他所有情况”，穷尽检查帮不上忙。这就是第二圈说“不写 default”的原因。

← ④ 机制 3

6. 预测：一个小工具在中文 Windows 上用 new FileReader("a.txt") 读 GBK 编码的文件，JDK 8 和 JDK 21 上结果一样吗？

不一样。8 上默认编码跟系统走（GBK），能正常读；21 上默认是 UTF-8（18 起），读 GBK 文件会乱码。显式指定编码就两边一致。

← ④ 表格“默认 UTF-8”+ 坑 5

7. 预测：17 上用 --enable-preview 编译的 class，拿到 21 上运行会怎样？

跑不起来。启用预览特性编出来的 class 文件带着版本标记，只能在编译它的那个 JDK 大版本上、并且同样加 --enable-preview 才能运行。
